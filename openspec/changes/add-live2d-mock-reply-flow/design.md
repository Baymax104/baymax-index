## Context

当前 Live2D 桌面人物和对话框已经具备基础交互：桌面端显示人物、点击展开或收起面板、消息列表展示用户提交的本地消息。现有流程缺少助手侧响应状态，用户提交后不会产生回复，也没有为后续大模型 API 接入预留清晰边界。

本变更在前端本地完成 mock 回复流程，主要影响 Live2D 对话相关组件、消息类型和配置。移动端继续沿用现有不显示、不加载 Live2D 的约束。

## Goals / Non-Goals

**Goals:**

- 建立助手回复生命周期：`idle -> thinking -> typing -> idle`。
- 使用 mock 数据模拟回复内容，先验证 UI、状态管理和打字机效果。
- 回复进行中阻止并发提交，避免多条回复流程互相覆盖。
- 面板收起不影响回复计时和消息状态，重新展开时显示当前进度。
- 将 mock 回复获取逻辑和时序参数放在可替换边界内，方便后续接入 LLM API。

**Non-Goals:**

- 不接入真实大模型 API、流式接口、后端代理或环境变量。
- 不实现多轮上下文压缩、联网检索、鉴权或错误重试策略。
- 不改变 Live2D 模型加载、桌面端显示策略或已有展开/收起动画目标。
- 不支持多个并发助手回复。

## Decisions

### 消息状态扩展

为 Live2D 消息增加助手回复状态，例如 `done`、`thinking`、`typing`。用户消息始终视为完成状态；助手占位消息先进入 `thinking`，开始输出后进入 `typing`，输出结束后进入 `done`。

备选方案是只新增全局 `isThinking` 和 `isTyping` 状态。该方案实现更少，但消息列表无法可靠表达“哪一条助手消息正在变化”，后续接入真实 API 或错误状态时也更难扩展。

### 单一回复状态机

提交非空消息后由组件内的单一流程驱动：追加用户消息，追加助手占位消息，等待 thinking 延迟，逐字填充 mock 回复，最后释放提交门禁。流程中的计时器需要在组件卸载时清理。

备选方案是允许每次提交都启动独立计时器队列。初版没有并发回复需求，会增加竞态和 UI 复杂度，因此先显式禁止并发提交。

### 可替换的 mock reply provider

mock 回复内容由单独函数或小模块提供，接收当前消息上下文并返回回复文本。初版可以轮换固定文案，但调用侧只依赖“获取回复文本”的抽象，后续可以替换为 API adapter。

备选方案是把 mock 文案直接写在提交 handler 中。该方案更快，但会把 UI 状态和回复来源耦合在一起，后续接入 API 时需要重写提交流程。

### 打字机效果在前端本地驱动

打字机效果通过固定间隔逐步更新当前助手消息内容。时序参数放入 Live2D 配置，便于调整 thinking 延迟和逐字速度。

备选方案是使用 CSS 动画裁剪文本。CSS 方案对动态文本、滚动定位和后续流式内容不够直观，状态完成时机也更难控制。

## Risks / Trade-offs

- 回复计时器在组件卸载后继续写状态 -> 在 effect cleanup 中集中清理所有 pending timers。
- 打字机频繁 setState 导致卡顿 -> 默认字间隔保持温和，并只更新最后一条助手消息。
- 面板收起时继续回复可能让用户错过过程 -> 这是为了保证“收起不取消”的一致性；重新展开后展示当前状态或最终回复。
- mock provider 边界设计过度抽象 -> 初版保持为一个轻量函数或模块，不引入复杂 service 层。

## Migration Plan

1. 扩展 Live2D 消息类型和配置，不影响现有已完成消息的渲染。
2. 将提交流程从“只追加用户消息”迁移为“用户消息 + 助手回复生命周期”。
3. 对回复进行中的输入或提交控件增加禁用态。
4. 使用 Playwright 验证桌面端交互、收起/展开保持进度、移动端不显示。

回滚时删除 mock 回复流程相关类型、配置和 provider，提交逻辑恢复为只追加用户消息。

## Open Questions

无阻塞问题。当前默认采用固定 mock 文案、thinking 延迟约 700ms、打字速度约 32ms/字符，后续实现可按视觉验证微调。
